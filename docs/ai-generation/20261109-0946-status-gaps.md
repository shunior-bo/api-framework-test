## Where CONVENTIONS.md was insufficient

- **Malformed JSON (400).** §8 Step 8 cites "400 needs malformed JSON, which the typed client can't send" as an example of a reason to skip a test. This run instead added explicit raw-body client methods (`createWithRawBody`, `updateWithRawBody`, `patchWithRawBody`) that still go through the fixture-built client, so coverage sees them. CONVENTIONS should say whether that is the preferred pattern. It should also add the method name to the §3 naming list (`…WithRawBody`), and decide whether one generic helper is better than one method per verb.
- **Response bodies the spec leaves undocumented.** The 400 body (`{ error: string, details }`) differs from `ErrorMessage` (`{ error: { message } }`). §5 only covers 401/409/422 and 404. A new `MalformedJsonErrorSchema` was added, with a docstring stating that it mirrors observed behavior. CONVENTIONS could list it next to `ErrorMessageSchema`.
- **PUT 201 (upsert) vs §6 "never PUT to `NON_EXISTENT_ID`".** The rule's goal (no leftover records) is met by cleaning up the returned id in `finally`. tc-articles-13 picks an id 1000 above the current maximum, computed in Arrange, and deletes `parsed.data.id`. GAD ignores the requested id and assigns a new one, which the §9 table could mention. CONVENTIONS could also state how a test should obtain "an unused id for PUT 201".
- **PATCH does not upsert**, so `NON_EXISTENT_ID` is safe for PATCH 404 (tc-articles-20 also checks that the id is still 404 afterwards). §6 only mentions GET and PUT.
- **DELETE on articles is a soft delete.** A PUT to a just-deleted id answered 200 instead of 201 in a curl probe. This is worth a §9 row, because any future "PUT after DELETE" test would hit it.
- **Split of `tests/unit/schema.spec.ts` changes across commits.** The schema unit test was committed with the `test:` batch commit, not the `feat:` commit; §11 does not say which.
